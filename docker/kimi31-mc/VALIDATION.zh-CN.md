匹配对应 PUT，失败/不匹配为零。该检查不是通用模型精度评测。

**不能声明所有负载均无回退。** 原 MC 是已完成完整压测的热进程，实验版是新进程；
后者 96 批 PUT 中有 8 批在 300–400 毫秒，其余 88 批均小于 50 毫秒，
因此初始 38.232 毫秒均值不能直接归因为持续的三倍写入回退。
针对这一冷启动疑点，只补了一对原 SWE 39964-token 冷写/清 GPU 回读诊断，
未重跑原比较组：同一实现的后续 24 批 PUT 均值 10.209 毫秒，8 批 GET
均值 27.851 毫秒，读写失败为零，两次回答正确。它支持首写初始化成本的解释，
但不同批大小/并发下的单对诊断不足以证明长期并发无回退。
一次空闲 SDK 分段写诊断也未稳定复现增幅；same-node grouping 没有足够证据作为
解决方案，不修改该默认配置。当时 compact 默认关闭，不用节省字节替代性能证据；
后续大批对照及默认开启的范围见本文末尾。

## 命中率结论与限制

完整 SWE 测试的 token 加权命中为 95.9722%，不是静态历史重复请求的命中率。
以上一轮成功输入、模板尾部及 2048 对齐构造的保守代理为 95.9476%；
因此不能将与 98% 的全部差距都当作 KV 丢失，也不能拿静态小批 98.5365% 替代它。

仍有四对请求经真实 token 公共前缀核对存在额外 34816 tokens 缺口，
约为整轮 7.146 亿输入 tokens 的 0.00487%。对应时间邻近 Master 容量淘汰，
但缺少逐 key 淘汰证据，尚不能声称已完全修复。
wrapped Mamba 分类及 decode checkpoint 保存上限有回归覆盖，
不把兼容性修复直接当作这四处缺口的根因或已实现收益。
额外 CPU 反事实检查保留三个 Mamba 组及 DCP8 全部分片：四例所需 key 齐全时
均命中完整对齐前缀；缺失一个必需分片或未发布最新 checkpoint 都能产生相同回退。
这不是原请求逐 key 重放，不据此虚构已排除所有驻留或写入异常。

## GPU 容量边界

本改动只缩短 Mooncake 对象及读写 extent，不修改 GPU 分页分配或内核布局，
不会将省下的 L2 字节转为额外 GPU KV 容量。
当前 GPU KV 逻辑总池为 16,159,561 tokens，DP1/TP8 不再乘以八。
每 rank 实际共享 backing 为 31,021,056,000 字节，1125 个 slot；不同组的
别名视图不能重复累加。最大组后约 1.081 GiB/rank 的尾隙来自内核页步长的
共同对齐要求；保持现有地址契约不能直接裁掉。Mamba 状态内部无可删 padding，
不删除 FP32 状态或 NVFP4 scales 来制造容量提升。

## 尾 checkpoint 写失败的后续修复

进一步核对原引擎日志，四处额外少命中的上一请求均出现 boundary PUT 的
`-200` 返回码：session/turn 为 1/47、80/71、82/48、127/81。
这将实际写失败关联到对应请求，不再只是淘汰时间邻近；但原日志没有逐 key
保存/淘汰/加载全链路，仍不把每次缺口的所有原因都归为已证明。

原恢复 gate 依赖未来 job 的探测；如果最新 checkpoint 此次未写成，原 job
退出后其 pinned 状态不能保证仍可取得。新增一次仅针对 boundary `-200`
失败 key 的有界补存，保持其它失败和永久空间耗尽时的保守回退。
重试沿用原 pinned 来源、保留首次失败计数，并校验 job 代际；正常路径不变。
持续错误受既有一秒 probe 期限限制，不按每个新请求重复等待。

CPU 先复现 7 failed / 4 passed，修复后专项 12 passed、worker CPU 34 passed、
相关回归 70 passed，pre-commit 通过。真实服务采用一个精确 Mamba 边界的一次
`-200` 注入，而后续补存与清 GPU 后 GET 使用真实 SDK；这不是制造物理容量耗尽。
