# GLM-5.3 Flash integration

## Source layout

- ${repo}/integrations/glm53flash/manifest.json pins three upstream revisions,
  image provenance, and the SHA256 of every changed source file.
- ${repo}/integrations/glm53flash/patches contains the deployed Python,
  native CUDA/CMake, FlashInfer and Router diffs. The vLLM base is
  5df63a7203cdb9328d824a27b682e77c7b9928be, version 0.32.0.
- ${repo}/integrations/glm53flash/experiments/prefill-only.patch contains the
  P-only admission experiment, separately from image defaults.
- Mooncake native core remains version 0.3.13.post1. Changes are in the vLLM
  connector/Store; the master uses a 0.98 eviction watermark and 750 GiB per
  D host. Payload layouts and encoding-specific key namespaces must match.

## Restore and build

Run from the branch checkout, using its Python environment:

~~~bash
.venv/bin/python integrations/glm53flash/prepare_sources.py sources
docker build -f integrations/glm53flash/Dockerfile \
  --build-arg BASE_IMAGE=local/glm53flash-vllm:build-base \
  -t local/glm53flash-vllm:0.32.0 .
(cd sources/router && cargo build --locked --release --lib)
docker build -f integrations/glm53flash/Dockerfile.router \
  --build-arg ROUTER_BASE_IMAGE=local/glm53flash-router:base \
  -t local/glm53flash-router:0.1.16 .
~~~

The build base is the retained CUDA 13 / Python 3.12 development image
33333ac91514 (full ID in the manifest), with Torch, CMake, Ninja and the
FlashInfer CUTLASS headers. The Router base is the retained Python 3.12
5d123a4a image. Cargo builds on Linux with the matching Python interpreter.
The native recipe builds only _C_stable_libtorch, retaining the existing
MoE and external extensions. It targets SM100-family and SM120-family
code (10.0f / 12.0f), including B300. Generated Marlin/Machete sources are
regenerated by CMake; installed third-party trees and binaries are not vendored.

For the P-only experiment, prepare a separate output directory using
--prefill-only-experiment. Use fixed-zero proposal budget [[1,64,0]] covering max_num_seqs and set the P
Mooncake producer extras mamba_current_state_only, release_finished_mamba_scratch,
and prefill_only_target_state to true, with remote_mamba_speculative_blocks=3. D keeps MTP3; no diagnostic worker RPCs,
CUDA-event hooks or temporary load generators are included.

## EP4 P data-parallel adaptation

- config/vllm.py preserves the P-only fixed-zero proposal schedule under DP when one interval covers every legal batch size.
- Nonconstant schedules, D roles, incomplete intervals and MTP5 keep the native DP disable guard.
- The KDA check accepts an all-zero interval covering max_num_seqs rather than requiring exactly 1–64.
- Idle-DP dummy proposal uses budget0 for the same P-only role instead of the global default3, aligning draft-prefill/collective count with active P ranks.
- Nine CPU cases execute the actual DP config method; four more exercise the actual role predicate and dummy budget expression.

## P admission and transfer findings

- Generic MTP allocation reserved three target-verification scratch states
  per KDA group on P. With 865 usable physical blocks, each short request
  needed 14 blocks: three KDA groups times four states, plus MLA and circular
  state. Sixty-four requests needed 896 blocks.
- The opt-in P patch removes target-verification scratch allocation when P
  uses proposal budget zero, retaining global MTP3 and draft-prefill state
  shapes. It maps P local zero and D remote three scratch slots separately.
- Finished-request scratch retirement uses request.last_sched_seq and the
  native processed-step fence. Store jobs retain their independent references.
- The connector resolves UniformTypeKVCacheSpecs.first_spec and transfers
  committed KDA state rather than trailing verification scratch.
